## Задача 1. Обеспечить разработку

Для разработки я предлагаю известный мне стек: **Yandex Cloud, GitLab (CI/CD, раннеры) и Nexus Repository**.

В качестве облачного провайдера можно взять Yandex Cloud. Для хранения исходного кода и управления CI/CD - self-hosted GitLab. Под каждый микросервис создаётся отдельный Git-репозиторий  со своим пайплайном =.

Процесс CI/CD организован следующим образом:

- несколько stages: сборка, тестирование, DevSecOps проверки
- При `push` в ветку `dev` автоматически  запускаются сборка и тестирование.
- После слияния Merge Request в `master` запускается пайплайн развёртывания.
- Собранные Docker-образы складываются в Nexus Repository, образы оттуда используются для деплоя .

Конфигурации сборок описываются в `.gitlab-ci.yml`. Для выполнения заданий GitLab Runner.

Для небольших MVP-проектов в команде используем runner непосредственно на целевой машине, что позволяет сэкономить на облачных VM. Для проектов в стадии production эксплуатации есть пара выделенных VM раннеров.

Для хранения секретов используются защищённые переменные GitLab CI/CD и HashiCorp Vault. Пароли, токены и ключи доступа не хранятся в репозиториях и передаются в задания пайплайна по необходимости.

Для окружений разработки у нас в команде используются PaaS решения **Coolify и Dockploy** c GitOps подходом.


## Задача 2. Логи

Для централизованного сбора и анализа логов я бы выбирал между двумя стеками, которые мы применяем в нашей команде: **ELK (Elasticsearch, Logstash, Kibana)** для ключевых сервисов компании и **Grafana + Loki** для остальных.

Elasticsearch предоставляет полнотекстовый поиск , но требует больше ресурсов. Loki индексирует только метки (labels), а сами логи хранит в сжатом виде. Для большинства сервисов поиска по меткам вполне достаточно. Это позволяет снизить расходы на хранение и обработку логов. ELK остаётся для критичных сервисов, где необходим глубокой поиск и анализ. 

Для сбора логов контейнеров на хостах используется Grafana Alloy, который отправляет данные в центральное хранилище Loki. Для ключевых сервисов можно организовать отдельный поток логов в Elasticsearch через Filebeat и Logstash.

Для поиска и анализа – **Kibana** или **Grafana**. Поисковые запросы в этих dashboard можно сохранять и передавать в виде ссылок.


## Задача 3. Мониторинг

Опять-таки могу предложить то что уже используется у меня на работе: **Prometheus, VictoriaMetrics, Grafana и Alertmanager**.

Сбор метрик организован через стандартные Prometheus exporters:

- **Node Exporter** — системные метрики хостов: CPU, RAM, использование дисков, дисковый I/O и сетевой трафик.
- **cAdvisor** — потребление ресурсов отдельными Docker-контейнерами: CPU, RAM, файловая система, дисковые операции и Network.
- **Application metrics** — специфичные для каждого микросервиса метрики, которые приложения публикуют через `/metrics`: количество запросов, время ответа, ошибки, состояние очередей и другие показатели.

Prometheus собирает метрики и передаёт их в **VictoriaMetrics**, которая используется как основное хранилище временных рядов.

VictoriaMetrics выбрана из-за производительности и эффективного использования ресурсов. При большом количестве метрик она, как правило, потребляет меньше RAM и дискового пространства, чем стандартное хранилище Prometheus, а также обеспечивает быстрый поиск по историческим данным.

PromQL для запросов и анализа метрик, визуализации через **Grafana**.  Для оперативной диагностики вполне годится интерфейс самого Prometheus.

Для оповещений используется стандартный **Alertmanager**, который группирует события, устраняет дублирование и отправляет уведомления ответственным сотрудникам.

Отдельно используем **Apprise** для доставки системных уведомлений. Например, предупреждения от ZFS, SNMP или S.M.A.R.T., которые системные демоны отправляют по электронной почте, через почтовый обработчик перенаправляются в Apprise и преобразуются в push-уведомления.

Параллельно применяем дополнительные инструменты мониторинга: **Pulse** для быстрого обзора состояния виртуальной инфраструктуры и контейнеров, **Netdata** для детальной диагностики хостов в реальном времени.

Альтернативные источник метрик дают больше гарантий, что ничего важного не было пропущено при ручной настройке Prometheus/VictoriaMetrics/Grafana.
