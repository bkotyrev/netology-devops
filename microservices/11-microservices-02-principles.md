# Микросервисы: принципы

## Задача 1. API Gateway

Для API Gateway можно рассмотреть **NGINX**, **Traefik** или все более популярной **Caddy**. В моей компании вместо NGINX используется OpenResty для тонкой настройки эндпоинтов со скриптами на LUA.

Сравнение по основным требованиям:

- **Маршрутизация запросов.** Ршения поддерживают маршрутизацию по URL и доменам. NGINX настраивается через конфигурационные файлы, Traefik удобен для Docker и Kubernetes поскольку поддерживает label- динамические настройки.
- **Аутентификация.** NGINX и Traefik могут передавать проверку запросов внешнему сервису авторизации.
   **HTTPS.** Все три поддерживают терминацию SSL/TLS. Traefik Caddy умеют получать и обновлять сертификаты Let's Encrypt.
- **Сложность обслуживания.** NGINX - проверенный вариант и очень экономный по памяти. Traefik удобнее в динамической контейнерной среде. Caddy можно взять на тестовый период, если не создаст проблем в производительности – можно вывести в прод.

Во всех случаях клиентам не нужно знать внутреннюю структуру микросервисов. Сохраняем обратную совместимость API, чтобы изменения на стороне микросервисов не ломали работу существующих клиентов.

## Задача 2. Брокер сообщений

Для асинхронного взаимодействия микросервисов можно выбврать между **RabbitMQ и Apache Kafka**. Оба инструмента позволяют обмениваться сообщениями между сервисами, но рассчитаны на несколько разные задачи.


- **Кластеризация.** Оба решения поддерживают работу в кластере и репликацию данных для отказоустойчивости.
- **Хранение сообщений.** RabbitMQ позволяет сохранять сообщения на диск до их обработки. Kafka хранит события в журнале в течение заданного времени, поэтому их можно читать повторно.
- **Производительность.** RabbitMQ хорошо подходит для очередей задач и обычного обмена сообщениями. Kafka лучше справляется с большими потоками событий.
- **Форматы сообщений.** Оба могут передавать различне форматы. Содержимое сообщения определяется самим приложением.
- **Разграничение доступа.** RabbitMQ поддерживает пользователей, права и виртуальные хосты. Kafka использует ACL для разграничения доступа к топикам.
- **Администрирование.** RabbitMQ проще в настройке, имеет удобный Web UI. Kafka несколько сложнее в эксплуатации.

Для обычного взаимодействия микросервисов RabbitMQ выглядит более простым решением. Его возможностей достаточно для очередей фоновых задач, передачи событий между сервисами и распределения нагрузки между обработчиками. Для отказоустойчивости можно использовать кластер из трёх узлов с кворумом.

Kafka я подходит для более сложных проектов, где требуется обрабатывать большие потоки событий, хранить историю сообщений и иметь возможность повторно их читать.
